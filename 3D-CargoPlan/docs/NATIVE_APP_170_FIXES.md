# CargoPlan 1.7 · 默认入口、装配编辑与真实计算进度

日期：2026-10-31。

## 为什么之前看不到新版

本次实机发现，用户实际启动的是 `/Applications/CargoPlan.app` 1.3.0；此前新版本并行装在另一个名称下，未更新默认入口。1.3 的知识栏、助手与装配行为均落后。

本次统一更新默认 `CargoPlan.app` 至 1.7.0，保留应用顶层目录标识，供原 Dock 入口继续使用；1.4、1.5、1.6 已从应用程序目录归档到用户的 `Library/Application Support/CargoPlan/Backups`。旧版不删除。

升级前已从实际旧 APP 导出 `CargoPlan-before-1.7.xlsx`，逐件比较 1,371 件的实装尺寸、位置和重量，与原基线一致。副本在 `output/native-170-validation/before-upgrade.xlsx`。

## 装配编辑

- 基础长宽高和重量支持回车、结束输入后保存；尺寸修改先转待装，原 3D 中移除该件，不自动求解。
- 转入待装后保留编辑器，可以继续改宽高。柜内件数、待装件数和下拉菜单同步更新，货物总数守恒。
- 完整参数继续复用方向、承重、堆叠及空腔表单，保存实际写回引擎输入。
- 货舱尺寸仍支持输入与 3D 手柄；缩小后移出越界 / 超载件，可撤销。
- 原生检查器可整体滚动，参数区不被货物列表挤出窗口。
- 个人工作区与待装状态自动保存在 `~/Library/Application Support/CargoPlan/workspace-v1.json`；正常退出同步保存，下次启动恢复。自动化测试及隔离验收不写入用户工作区。

当前原生基础尺寸编辑采取保守处理：修改的货物先待装，由主动计算决定新位置；并非宣称只凭外包尺寸就能证明支撑、空腔和方向约束全部有效。

## 为什么原来总要 20 秒

旧流程即便已获得通过校验的完整修复方案，也继续做全量搜索，直到时间预算用完。原流程设置 20 秒搜索预算；本轮基线快速修复约 1.3–3.1 秒，仍为 11 柜、1,371 件全装入。此耗时只对应未改动的伊拉克基线，不是任意输入的时延保证。

新增两种主动模式：

| 模式 | 行为 |
| --- | --- |
| 快速修复（默认） | 优先保留已校验方案；完整修复成功则提前返回。不完整时在较短预算内继续尝试。 |
| 深度优化 | 用户主动选择后，继续搜索并与有效修复方案比较，原生预算 20 秒，可取消。 |

原生和网页工作台共用同一模式与求解入口。快速模式不保证最少柜数；遇到复杂修改仍可能有待装件，可选择深度优化。不会为追求速度把未装件标成已装。

对明显所有允许方向都超空间的货物，先筛掉不适配方向，再生成候选位置；保留原 PDF 的专项高度例外。剩余插入预算在待装货物与候选柜之间分配，避免一件难放货物独占全部剩余时间。

## 真实进度

修复和贪心搜索上报已检查件数、总件数、本候选柜数、已分配与未装件数。协调器将实际阶段与件数转换为单调百分比，经逐行 JSON 从本地引擎流入原生进度条；网页 Worker 使用相同事件。

百分比表示本次流程阶段进度，不表示已经找到全局最优，也不是 20 秒计时动画。计算期间保留旧 3D；独立校验完成后统一更新。取消后停止子进程，旧回调不覆盖当前工作区。
