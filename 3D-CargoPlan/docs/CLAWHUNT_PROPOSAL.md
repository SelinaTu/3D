## 1. 背景

### 1.1 起点：一份真实的工程货物清单

团队此前接触过一个门窗出口项目（以下称“Villa 项目”，已脱敏）。清单有门窗、玻璃架、辅材三张表，90 行，展开后 1371 件、约 134.8 t、590 m³。难点不在件数，而在约束：

| 清单原文（节选） | 竞品表单能否表达 |
|---|---|
| “顶部只能叠放自身相同物品”，“叠放自身相同物品不限制重量” | 部分可以（自叠），但“同类不限重”这种条件规则通常没有字段 |
| 玻璃架“可叠放对象：非自身相同物品”，顶部最大 600 kg | “只能承托其他类货物”是反向条件，常规“是否承重”字段表达不了 |
| 框“空腔内可放置尺寸适当的辅材或框扇，如果空腔内放框扇，框扇必须侧放” | 嵌套装载加条件方向，常规立方体装箱不支持 |
| W02 “允许侧放，侧放后高度 2560 mm，对该物品允许突破摆放高度限制” | 单品例外规则，需要人工处理 |
| “1# 和 3# 玻璃架宽边并排入柜 1114+1182=2296，有利于顶部摆放其他物品” | 老师傅经验，属于布局建议，无字段 |
| 门窗编号区分 W04(1F)、W04(2F)，项目覆盖 Villa 2 和 Villa 3 两栋 | 隐含“按楼栋、楼层分批到场”的收货需求 |

此前团队用约束求解完成过单站点装柜（11 柜全部装入、独立校验通过），但“尽量靠柜门”只是软偏好，**没有处理装卸顺序**。这正是本方案要解决的部分。

> 合规说明：比赛规则要求“Competition code and assets must be produced during the event”。参赛代码全部在活动期间新写，旧项目只作为领域经验。演示数据从源清单派生并脱敏，是否允许使用需向主办方确认（见第 11 节）。

### 2.2 公开资料中未见的空白

| 空白 | 证据 |
|---|---|
| 异形货 | 悠闲装箱功能页写明“仅适用于近似立方体形状的货物装箱，圆柱、锥形和其他异形货物暂不支持” |
| 条件约束和嵌套 | 各家约束均为表单字段（是否承重、自叠层数、承重级别），无“空腔内放框扇须侧放”这类条件规则 |
| 倒货次数 | “按组顺序”只能预防，未见任何产品计算倒几次、哪件挡哪件 |
| 逐段重心 | 重心校验针对装完时刻，未见卸掉一站后重新校验剩余货物 |
| 中途装卸混合 | “按组顺序”默认全部在起点装货，未见“B 站卸一部分再装新货”的场景 |
| 约束出处与拒绝理由 | 未见 Agent 解释“这条规则来自哪一格”“你的改动为何被拒” |
| 机器人可读任务数据 | 输出为 Excel、Word、二维码，面向人 |

以上只代表“三家国内官网和 EasyCargo 公开页面未见”，不等于竞品做不到。清瞳载观、傲林科技、互邦、算立方、广域铭岛等企业级方案尚未核实，评审前补齐。

### 2.3 机器人装卸的趋势

Pickle Robot、Boston Dynamics Stretch 等卸货机器人已商用，主要依靠视觉在现场识别随机堆放的箱子。装卸规划和机器人执行之间目前没有标准接口。判断：机器人越普及，方案越需要给出**确定的顺序、位姿和每一步的可行性**。人能容忍“大概这么放”，机器人不能。（该判断为团队观点，非市场数据。）

## 4. 愿景与定位

### 4.1 愿景

**让货物从装车到最后一站卸完，每一步都做得到、成本最低、有依据。**

| | 竞品 | CargoPlan Agent |
|---|---|---|
| 优化对象 | 单次装载的利用率、柜数 | 全程总成本：可行性 > 倒货次数 > 柜数 > 工时 > 利用率 |
| 输出物 | 给人看的 3D 图和步骤图 | 可验证的逐站作业序列，人和机器人都能执行 |
| 约束来源 | 用户填表单字段 | Agent 从单据和经验中提取，每条有出处，人工确认后生效 |
| 校验时点 | 装完那一刻 | 每一站卸货/装货之后 |

### 4.2 三阶段路线图

| 阶段 | 形态 | 关键能力 |
|---|---|---|
| 一：人工作业指导（本次黑客松 MVP） | 计划员和装卸工使用 | 约束证据链、倒货最少、逐站回放 |
| 二：人机协同 | 输出给机器人仿真和 WMS | 标准化任务数据、位姿、坐标系、接口文档 |
| 三：机器人原生 | 方案成为作业接口 | 实际放置偏差回传后自动重规划（闭环） |

阶段二、三只作为路线图，本次不宣称实现。

### 4.3 不做什么

- 不与竞品比拼纸箱装柜利用率或免费额度。
- 不做路线规划（站点顺序作为输入）。
- 不控制真实机器人，不做感知、抓取点、夹具和轨迹。

## 5. 产品设计

### 5.1 用户旅程（计划员视角）

1. **导入**：上传货物 Excel 和站点表（站点顺序、每站卸货/装货清单）。
2. **约束确认**：Agent 列出提取的规则卡片，每张标明原文、来源单元格、置信度和结构化结果。低置信度项必须人工确认。
3. **规划**：一键生成方案，同时给出“按站分组”基线做对照。
4. **审阅**：3D 逐站回放；查看每站阻挡清单、倒货次数、每段重心和预估工时。
5. **调整**：拖动货物或用一句话下指令（“B 站多了 10 件 W05”“C 站的玻璃架放门口”），系统重新校验，拒绝时引用具体规则。
6. **交付**：导出装车作业单、逐站卸货单、任务数据 JSON、约束与版本记录。

### 5.3 Agent 工作流

```
Excel/站点表 ─▶ ① 解析（确定性代码）
                    │ 结构化字段 + 原文备注
                    ▼
              ② 约束提取（LLM）──▶ 规则卡片：原文 / 单元格 / 结构化规则 / 置信度
                    │
                    ▼
              ③ 人工确认（UI）──▶ 已确认规则集（带版本号）
                    │
                    ▼
              ④ 求解（确定性求解器，LLM 不参与坐标计算）
                    │
                    ▼
              ⑤ 独立校验（与求解器分开实现）──▶ 通过 / 违规清单
                    │
                    ▼
              ⑥ 解释（LLM）──▶ 取舍说明，每句引用规则 ID 或指标
                    │
                    ▼
              ⑦ 重规划：用户一句话 → LLM 转成结构化改动 → 回到 ④
```

**设计原则**

- LLM 只做三件事：把自然语言转成结构化规则、把用户指令转成结构化改动、把结果翻译成解释。坐标、可行性、指标全部由确定性代码计算。
- LLM 产出的规则必须通过 JSON Schema 校验；不合规则回退为“待人工确认”，不静默丢弃。
- 每次求解结果绑定规则集版本号和输入哈希，可重放。
- 解释中的数字只能引用求解器输出，不允许 LLM 自行生成数字。

## 6. 技术方案

### 6.1 模型与坐标系

- 单位：mm、kg。坐标原点在箱体内前壁左下角；x 沿箱长指向柜门，y 沿箱宽，z 向上。
- 货物：外包盒长方体加若干可选空腔；允许姿态集合由规则决定（MVP 只用绕 z 轴旋转和规则允许的侧放）。
- 站点：有序序列 `S1..Sn`。每件货有 `loadStop` 和 `unloadStop`；起点装货的 `loadStop = S0`。
- 柜门：单侧，位于 x = L。取货方向为沿 -x 反向平移到门口，再从门口取出。

### 6.2 阻挡与倒货的定义

在站点 `k` 卸货前，对目标货 `i`（`unloadStop = k`），若剩余货物 `j` 满足以下任一条件，则 `j` 阻挡 `i`：

1. **上方压住**：`j` 的底面高于等于 `i` 的顶面，且两者在 xy 平面投影重叠。
2. **门侧挡住**：`j` 的 x 区间整体位于 `i` 与柜门之间，且两者在 yz 平面投影重叠。

阻挡关系递归计算（挡住 `j` 的货也必须先移）。**倒货次数**等于为取出站点 `k` 全部目标货而必须临时移出、又要放回的非目标货件数，所有站点求和。

MVP 假设：直线平移取货，不考虑叉车或机械臂本体体积，不考虑倾斜取出。这些假设在 UI 和导出文件中显式标注。

### 6.3 求解器

**目标（字典序）**：可行 > 倒货次数最少 > 每段重心偏移最小 > 预估工时最少 > 体积利用率最高。

**构造阶段**

1. 按 `unloadStop` 从晚到早分组，最晚卸的组放最里面（靠前壁），最早卸的组靠柜门。
2. 组内用极点法（extreme point）摆放，按底面积降序、重量降序排序；候选位置评分加入“对后续组形成阻挡”的惩罚项。
3. 中途装货（`loadStop > S0`）：在前一站卸货后的空闲空间内摆放，候选位置必须不阻挡 `unloadStop` 更晚的货。

**改进阶段（限时）**

- 邻域操作：跨组边界交换、组内重排、姿态切换、整列平移。
- 搜索：模拟退火或禁忌搜索，每个候选都用独立校验器的快速版评估。
- 时间预算 5 到 30 秒，超时返回当前最好可行解，并标注“非最优证明”。

**基线**：同一求解器只执行“按站分组 + 组内极点法”，不做阻挡惩罚和改进阶段，用于模拟竞品“按组顺序装载”的策略。演示时明确说明这是团队自己实现的基线，不是竞品的真实输出。

### 6.4 独立校验器

与求解器分开实现，避免“自己验证自己”。逐项检查：

| 类别 | 检查项 |
|---|---|
| 完整性 | 每件货恰好出现一次；ID、尺寸、重量与源清单一致 |
| 几何 | 不越界、不重叠、姿态在允许集合内 |
| 支撑 | 底面支撑比例、禁止悬空、错位叠放限制 |
| 承重 | 累计顶部载荷、叠放层数、允许承托对象 |
| 逐站可取 | 每站按作业序列执行后，目标货可沿 -x 平移取出 |
| 逐站稳定 | 每次移出后，剩余货物仍满足支撑；被支撑件不能先于支撑件被抽走 |
| 逐段重心 | 每段运输开始时，剩余货物重心在允许范围内（箱体纵向、横向偏移阈值可配置） |

校验失败时返回违规项、涉及的货物 ID 和触发的规则 ID，供 Agent 解释。

### 6.5 工时模型

`工时 = Σ 正常装卸件数 × t_move + Σ 倒货件数 × (t_move × 2 + t_stage)`

`t_move`（单件搬移）和 `t_stage`（临时堆放和找位）按“人工 / 叉车 / 机器人”三档配置，默认值来自访谈；访谈前使用标注为“假设”的占位值。演示只报告件数和由参数推算的工时，不报告节省金额。

### 6.6 机器人任务数据（草案）

```json
{
  "planId": "plan-20261031-003",
  "ruleSetVersion": 3,
  "frame": { "origin": "container.front-left-bottom", "units": "mm", "axes": "x→door, y→right, z→up" },
  "stop": "S2",
  "tasks": [
    { "seq": 1, "op": "relocate", "itemId": "W05-017", "from": { "pos": [10450, 320, 0], "yaw": 90 }, "to": "staging-A", "reason": "blocks W03-004" },
    { "seq": 2, "op": "unload",   "itemId": "W03-004", "from": { "pos": [9800, 0, 0], "yaw": 0 }, "dims": [1530, 1330, 120], "weightKg": 37.3 },
    { "seq": 3, "op": "reload",   "itemId": "W05-017", "from": "staging-A", "to": { "pos": [9800, 0, 0], "yaw": 90 } }
  ],
  "assumptions": ["straight-line extraction along -x", "no manipulator volume", "rigid uniform density"],
  "status": "simulation-only"
}
```

`status: simulation-only` 是固定字段。没有感知、抓取点、夹具、轨迹规划和安全认证，数据只用于仿真和接口讨论。

### 6.7 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 前端 | React + TypeScript + Vite | 团队熟悉，构建快 |
| 3D | three.js（@react-three/fiber） | 实例化渲染可撑住数百件；逐步动画方便 |
| 求解与校验 | TypeScript，运行在 Web Worker 或 Node | 前后端共用一套模型；不阻塞 UI |
| Agent | Claude（经 AwwO 或 toklens 额度），工具调用 + JSON Schema 输出 | 规则提取、指令解析、解释 |
| Excel | SheetJS | 浏览器端解析，数据不出本机 |
| 3D 资产 | Tripo 生成卡车、叉车模型（可选） | 3D 赛道展示 |
| 部署 | 静态前端 + 轻量 API（Zion 云资源或本机） | 演示稳定优先，准备离线兜底 |

数据安全：赞助方 token 不含零数据保留协议。发给 LLM 的只有脱敏后的规则文本，客户名、项目名、单价不出本机。

### 7.2 五分钟演示脚本（决赛）

| 时间 | 画面 | 讲述要点 |

### 7.3 兜底方案

- 每个关键画面录屏备份；网络或 LLM 故障时切换到预先缓存的规则卡片和方案（UI 标注“缓存结果”）。

## 9. 商业化

### 9.1 目标客户（按优先级）

| 细分 | 为什么痛 | 购买者 | 验证问题 |
|---|---|---|---|
| 工程物流 / 门窗幕墙、钢构、设备出口商 | 货物异形、约束复杂、一柜货值高，返工代价大 | 物流经理、项目经理 | 每月排几柜？人工排一柜要多久？近半年返工几次？ |
| 中途装卸的专线、零担车队 | 多站倒货直接消耗工时和时效 | 调度主管 | 每趟几站？倒货占装卸时间多少？ |
| 卸货机器人集成商 | 需要上游给出可执行的作业序列 | 方案架构师 | 现在用什么数据格式？愿意为接口付费吗？ |
| 货代 | 替客户做装柜方案，需要可追溯的证据 | 操作主管 | 方案出错时怎么对账？ |

### 9.2 收费方式（假设，待访谈验证）

| 方式 | 内容 | 适合客户 |
|---|---|---|
| 按方案计费 | 每个多站点方案单次收费 | 低频出口商 |
| 团队席位订阅 | 不限方案数，含规则库沉淀 | 高频车队、货代 |
| 企业 API | 按调用量计费，含任务数据接口 | 机器人集成商、WMS 厂商 |
| 实施服务 | 客户规则库初始化、系统对接 | 大型制造企业 |

价格数字在完成至少 3 个访谈后再定，评审时只报区间假设和验证计划。

### 9.3 护城河

1. **规则库**：每个客户确认过的规则卡片会沉淀为行业约束库（门窗、玻璃、钢构等），新客户导入后可直接复用。
2. **可执行性数据**：逐站作业序列和现场反馈积累后，可用来校准工时模型和阻挡判定。
3. **接口位置**：在机器人进入装卸之前，先成为“方案 → 执行”之间的标准数据层。

### 9.4 活动期间的验证动作

- 10/31 的 Demo 市集收集至少 3 条反馈（议程要求），优先找物流、仓储、机器人背景的人。
- 赛前或赛中电话访谈 2 到 3 位工程物流或车队从业者，记录倒货频率和人工排柜耗时。
- 注册悠闲装箱、装箱大师试用账号，导入同一份脱敏清单，截图记录哪些规则无法填入（作为演示素材）。

## 11. 风险与待确认事项

### 11.1 需向主办方确认（10/30 当天）

| 事项 | 影响 | 默认处理 |
|---|---|---|
| 旧项目经验与数据能否使用 | 规则要求代码与素材在活动期间产出 | 代码全部新写；数据若不允许则改用按同类约束构造的合成数据 |
| 一个项目能否兼报多个赛道 | 每赛道取前 2 名进决赛 | 主报 Agent，3D 和商业化作为亮点 |

### 11.2 技术与产品风险

| 风险 | 可能性 | 应对 |
|---|---|---|
| 改进阶段在时限内不能稳定优于基线 | 中 | 停止线后只展示阻挡检测和校验；不宣称优化幅度 |
| LLM 规则提取错误或格式不合规 | 中 | Schema 校验、低置信度强制人工确认、缓存兜底 |
| 3D 逐步动画性能不足 | 低 | 演示控制在 60 件内；实例化渲染 |
| 现场网络或 token 中断 | 中 | 本机运行；录屏；缓存结果 |
| 评委质疑“竞品也能多站” | 高 | 主动承认红海部分，用倒货次数和逐段重心的对照数字说明差异 |
| 演示站点被认为是编造 | 中 | 显著标注为演示假设，并说明来自清单楼栋/楼层编号 |

### 11.3 模型边界（演示和导出中显式声明）

- 直线平移取货，不考虑叉车、机械臂本体体积和倾斜取出。
- 刚体、均匀密度、静态接触载荷；不覆盖绑扎、运输动力载荷和包装强度。
- 重心校验为箱体纵横向偏移阈值，非车辆轴荷认证。
- 工时参数在访谈前为假设值。
- 任务数据仅用于仿真，不能直接控制机器人。
